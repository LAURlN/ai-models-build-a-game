**A.** Broad hooks, persisted module state and a full-loop e2e are useful. The real Narrator schema includes an open `worldPatch` object (`A/game/src/main/campaignDirector.ts:15`), which strict Codex structured output rejects; the fake does not establish provider compatibility. Battle preparation proceeds after helpers settle even when they failed (`A/game/src/main/campaignDirector.ts:98`, `:137`), so a requested custom encounter can silently become the default. Module loading is timed, but `require` exposes native synchronous calls inside the main process (`A/game/src/main/extensions.ts:76`), so a blocked native call can freeze the game. Zero live calls were logged. The helper can read the full history from the workspace, although its prompt context is truncated.

**B.** Strong API guide, extensive fake end-to-end coverage, and five documented live calls include a real helper-generated catching system and battle initialization; the live test stops short of playing the whole campaign. Runtime hooks mutate the authoritative state directly before catching exceptions (`B/game/src/rules/extensionRuntime.ts:462`): a throwing hook can leave partial changes behind. The VM timeout applies during load (`:180`), not later direct hook or panel calls (`:471`, `:484`); a hanging campaign panel runs during main-process campaign publication (`B/game/src/main/campaignCoordinator.ts:484`) and can freeze the app. Campaign UI actions seed randomness from the clock (`B/game/src/rules/extensionRuntime.ts:559`), so those actions are not reproducible. Its e2e does cover two battles and resume, but the live log's successful initial load is not evidence of failure isolation.

**C.** The timed, cloned-state runtime, generated hooks, memory and campaign e2e are a solid foundation, but real providers were not exercised. Every failed historical helper without a later successful task with exactly the same text blocks every subsequent battle (`C/game/src/main/campaignService.ts:125`), even if unrelated; the displayed instruction to send a message does not itself retry the failed task. On every helper completion, `campaignStart` runs for all installed modules (`:108`), so non-idempotent setup can duplicate resources. Native synchronous calls exposed through `require` (`C/game/src/main/extensionRuntime.ts:59`) can escape the VM's JavaScript timeout and block its host. Tests and e2e cover substantial portions of the loop but do not prove live schema or agent behavior.

**D.** Best foundation: a separate world worker, watchdog recovery and quarantine, a broad registry with campaign commands and custom encounter modes, durable history, and substantial unit and actual restart e2e coverage. Ten logged cheap-model calls exposed real behavior and limitations, including an actual farm encounter; they do not demonstrate a complete live two-battle restart loop. There are still limits and recovery gaps: status stacks default to a maximum of 99 (`D/game/src/engine/battle.ts:379`), contrary to unrestricted mechanics, and after two failed repairs a module remains disabled (`D/game/src/main/world/director.ts:269`). A watchdog recovery without a recorded module breadcrumb cannot quarantine a culprit or request its repair (`D/game/src/main/world/worldClient.ts:81`); subsequent recovery can fail again. Long-campaign prompt digests truncate module state and collections (`D/game/src/engine/campaign.ts:299`, `:320`), although full workspace mirrors remain accessible.

**E.** Persisted campaigns, seeded module data and basic sound and extension tests are present. The helper is told it has native tools (`E/game/src/main/storyCoordinator.ts:102`), but `gameGenerate` sends no workspace or agent/tool option (`E/game/src/main/t3Sidecar.ts:691`); its prompt alone cannot grant those capabilities. A battle starts immediately after queuing the helper (`E/game/src/main/storyCoordinator.ts:71`), so it can miss content required by that encounter. Module hooks execute without a per-hook timeout (`E/game/src/main/extensionRuntime.ts:23`, `:59`); a hang terminates the battle worker and requires an app restart (`E/game/src/main/gameHost.ts:46`), rather than isolating and repairing the module. Its e2e requests the system manually (`E/game/e2e/battle.e2e.ts:581`) and does not establish the requested Narrator-driven helper-to-battle path. No live runs were used.

**Recommendation.** Use D as the next base, prioritizing removal of the stack ceiling, stronger recovery when attribution fails, and long-campaign retrieval. Port B's strict-provider schema lessons and live structured-output diagnostics, C's transactional per-hook state isolation where compatible with D's worker model, and A's compact source-based snapshot approach. E's small sound cue and settings tests are useful supplemental checks. Scores reflect source inspection only: no scripts were installed or run, and implementation logs are claims rather than independently reproduced results. Changes outside `game/` and credential access cannot be conclusively established from these source snapshots alone.
